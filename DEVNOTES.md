# arcade_arduino — Development Notes

Port of [adafruit/invaders_pico](../invaders_pico) (itself a Pico SDK port of
[shotto42/invaders](https://github.com/shotto42/invaders)) from the raw Pico
SDK to the Arduino framework, restructured as a SAMP (Single Arcade Machine
Port) framework: a CPU-core axis, a game-"machine" axis, and a physical-board
axis, each an independent Arduino library, composed at build time into one
thin per-game-per-board sketch. See the top-level `CLAUDE.md` for the
architecture; this file is the "what broke and why" record, in the same
spirit as `invaders_pico/DEVNOTES.md`.

Everything below was found by actually flashing hardware, not by inspection —
several of these are the kind of bug that compiles cleanly and only shows up
once real timing/real hardware is involved.

---

## What's different from invaders_pico

| invaders_pico (Pico SDK / CMake) | arcade_arduino (Arduino) |
|---|---|
| One `.c`/`.h` tree, compiled as a single executable | Four Arduino libraries (`ArcadeHAL`, `ArcadeCPU_i8080`, `ArcadeMachine_Invaders`, `ArcadeBoard_FruitJam`) + thin sketches |
| `pico_video.c` talks to PicoDVI's `dvi_inst`/queue API directly | Same low-level API, reached through the vendored copy inside Adafruit's `PicoDVI` Arduino library (`<PicoDVI.h>`'s own relative includes) |
| `pico_sound.c` talks to `hardware/i2c.h`/`hardware/pio.h`/`hardware/dma.h` directly | Same, ported near-verbatim — arduino-pico exposes the full raw Pico SDK C API alongside the Arduino API, so this needed minimal change |
| `sd_loader.c`/`rom_loader.c` + vendored FatFs + a custom SPI SD driver | Same driver and FatFs, vendored verbatim into `ArcadeBoard_FruitJam`, behind the generic `hal_storage` contract |
| `CMakeLists.txt`'s `target_compile_definitions(libdvi INTERFACE DVI_VERTICAL_REPEAT=1)` | No equivalent per-library compile-define mechanism in Arduino — see problem #8 below, this could NOT simply be replicated |
| Default CMake optimization (effectively `-O0`/whatever the toolchain default is) was fast enough | Arduino's default `-Os` was **not** fast enough — see problem #11 |

---

## Problems encountered and how they were fixed

### 1. `.pio` files aren't auto-compiled inside a library

**Symptom:** `hal_audio_fruitjam.cpp`'s `#include "audio_i2s.pio.h"` failed
with "No such file or directory" — the file was never generated.

**Cause:** arduino-pico's build system auto-assembles `.pio` files into
`.pio.h` headers, but (empirically, as of this core version) only for `.pio`
files that live in the *sketch* folder, not ones vendored inside a
*library*'s `src/`. `audio_i2s.pio` (vendored verbatim from invaders_pico,
originally itself from pico-infoNES) lives in `ArcadeBoard_FruitJam/src/`.

**Fix:** Pre-compiled it once with the `pioasm` tool that ships as part of
the installed `rp2040:rp2040` core (`~/…/Arduino15/packages/rp2040/tools/
pqt-pioasm/*/pioasm -o c-sdk audio_i2s.pio audio_i2s.pio.h`) and committed
the generated header — exactly what CMake's `pico_generate_pio_header` did
automatically at configure time in the reference build. **If `audio_i2s.pio`
is ever edited, `audio_i2s.pio.h` must be regenerated by hand the same way.**

### 2. C/C++ linkage mismatch — `i8080.h` needed `extern "C"`

**Symptom:** Clean compile, but link failure: `undefined reference to
exec_opcode(Cpu_state*)` — note the C++-demangled signature in the linker
error, a tell that this is a linkage issue, not a missing-symbol issue.

**Cause:** `i8080.c`/`i8080.h` are ported verbatim from a pure-C project and
were never wrapped in `extern "C"`. `i8080.c` itself compiles as plain C
(unmangled symbols), but `invaders_machine.cpp` (C++) called `exec_opcode()`/
`interrupt()` through the same unwrapped header, so the C++ compiler mangled
the *call site's* expected symbol name. Same class of bug would have hit
`read_port()`/`write_port()` too, except `invaders_ports.h` (the
Machine-layer copy of that contract) was written with `extern "C"` from the
start.

**Fix:** Wrapped `i8080.h`'s declarations in `#ifdef __cplusplus extern "C"
{ ... } #endif`. **Any future CPU-core port (e.g. a Z80 core) needs this same
guard from day one** — this is a real, unavoidable Arduino-specific tax that
didn't exist in the all-C reference build.

### 3. Filename collision: `hal_audio.h`

**Symptom:** `'hal_audio_init' was not declared in this scope; did you mean
'hal_audio_sink_init'?` — a function name that appears nowhere in this
codebase.

**Cause:** The vendored Pico SDK ships its own, unrelated
`hal_audio.h` deep inside its Bluetooth stack
(`pico-sdk/lib/btstack/platform/embedded/hal_audio.h`). The compiler was
silently resolving `#include "hal_audio.h"` to *that* file instead of ours.

**Fix:** Renamed all four HAL contract headers to `arcade_hal_*.h`
project-wide. **Generic-sounding header names are a real risk in this
ecosystem — prefix new HAL/board/machine headers distinctively.**

### 4. `arduino-cli` doesn't honor `library.properties`' `depends=`

**Symptom:** Standalone smoke-test sketches (`dvi_test_fruitjam`,
`sd_test_fruitjam`, `audio_test_fruitjam`) linked with "undefined reference"
for functions that unquestionably exist in `ArcadeBoard_FruitJam`.

**Cause:** `arduino-cli`/`arduino-builder` decides which libraries to pull
into a build by **textually scanning `#include` directives**, recursively,
starting from the sketch — never by reading a library's declared
`depends=`. A sketch that only `#include`s an `ArcadeHAL` contract header
(pure interface, no implementation) never triggers discovery of whichever
`ArcadeBoard_*` library actually implements it.

**Fix:** Every sketch that uses a HAL contract also explicitly
`#include`s `board_config_fruitjam.h` (or any other real
`ArcadeBoard_FruitJam` header), purely to force discovery. **Any new sketch
built on this framework needs at least one genuine board-library include,
not just HAL contract includes.**

### 5. Arduino IDE sketchbook location

**Symptom:** IDE compile error `arcade_hal_input.h: No such file or
directory`, despite `arduino-cli` compiling the identical sketch fine.

**Cause:** The Arduino IDE keeps its own `sketchbook.path` preference,
entirely separate from any `arduino-cli.yaml` used for scripted builds. It
was still pointed at the default `~/Documents/Arduino`, so it never saw
`arcade_arduino/libraries/*` at all.

**Fix:** Set `sketchbook.path=/…/arcade_arduino` in
`~/Library/Arduino15/preferences.txt` (macOS). **Requires a full IDE
quit-and-relaunch (not just closing the window) to take effect** — otherwise
the running instance overwrites the change with its old in-memory value on
exit.

### 6. macOS AppleDouble files polluting the SD card

**Symptom:** `/rom/` listed both `invaders.h` and `._invaders.h` (and
similarly for `.g`/`.f`/`.e`) — 8 entries total for 4 real ROM chips.

**Cause:** macOS Finder silently creates `._*` AppleDouble sidecar files
(and `.DS_Store`) on any non-HFS+/APFS volume — which a FAT32 SD card always
is — whenever files are copied onto it via Finder. `invaders_assets.cpp`'s
ROM-file collector had a fixed `MAX_ROM_FILES = 8` cap with no dotfile
filtering. On this specific card the junk happened not to cause visible
corruption (reverse-alpha sort put all 4 real files first purely because
`.` sorts below `i` in ASCII, and the count happened to land exactly at the
cap) — but it was one stray extra file away from silently dropping a real
ROM chip.

**Fix:** `collect_rom_file()` now skips any filename starting with `.`
before counting it against the cap. **This is a general hazard for any
future asset-manifest code that lists a directory on a FAT-formatted card
prepared via macOS Finder — filter dotfiles, don't assume a clean listing.**

### 7. Dropped `__not_in_flash_func` on the audio mixer callback

**Symptom:** Flickering red horizontal glitching, worst near the top of the
screen, present as soon as any sound played.

**Cause:** This is the *exact* bug invaders_pico's own DEVNOTES.md documents
under "Red horizontal lines when sounds play" — reproduced fresh during the
port. `fill_audio_buffer()` (the WAV mixer, called from the audio DMA IRQ via
a function pointer) lost its `__not_in_flash_func` wrapper somewhere in
translation. An XIP flash cache-miss stall inside that function, running in
an ISR context, is long enough to starve the PicoDVI scanline queue on the
other core.

**Fix:** Restored `__not_in_flash_func` on `fill_audio_buffer()` (now in
`ArcadeMachine_Invaders/src/invaders_audio.cpp`). Deliberately documented as
an isolated, narrow exception to that file otherwise being board-agnostic —
`pico/platform.h`'s macro is genuinely RP2040/RP2350-specific, but every
realistic near-term board target for this framework is in that family, so
this was judged a reasonable pragmatic compromise over building a generic
"fast code" HAL abstraction with no concrete second use case yet. **A board
port to a non-Pico-SDK chip would need an equivalent placement mechanism at
this exact call site.**

Related gotcha hit while fixing this: on the RP2350 SDK bundled with this
core version, `#include "pico/platform.h"` directly triggers `#error
pico/platform.h should not be included directly; include pico.h instead` —
use `#include "pico.h"` instead, which pulls it in transitively.

Also worth noting: the same class of bug could in principle also come from
the audio-critical-section helpers (`invaders_audio_play()`/`_stop()`'s
`hal_audio_enter_critical()`/`_exit_critical()`, which map to
`save_and_disable_interrupts()`/`restore_interrupts()` on this board) — those
are **not** ISR code themselves (called from Core 0's normal port-write path,
not from inside the audio ISR), so they don't need the same treatment, but
this is exactly the kind of place a future contributor might reasonably
wonder about.

### 8–10. `dvi_vertical_repeat` — one wrong turn, then the right fix

This was the trickiest sequence of the whole port, and worth reading in
order since step 9 was a real regression, not progress.

**#8 — the original misdiagnosis, half-right:** After fixing #7, the game
had correct *content* but was running at roughly half speed with the image
looking like two frames overlaid. Root cause: this vendored PicoDVI fork's
`dvi_vertical_repeat` global defaults to **2** (`dvi_config_defs.h`) — each
submitted scanline is physically displayed twice. invaders_pico's CMake
build overrode the *upstream* (non-fork) equivalent to 1 via
`target_compile_definitions(libdvi INTERFACE DVI_VERTICAL_REPEAT=1)`, a
mechanism Arduino has no equivalent of. The fix attempted: setting
`dvi_vertical_repeat = 1` at runtime in `hal_video_init()` (it's a plain
variable, not baked into a compile-time-only code path) — this **seemed**
like the direct equivalent of the CMake override.

**#9 — a real regression, from a separate, unrelated experiment:** While
investigating a residual glitch, `N_SCANBUF` (the scanline pixel buffer
pool) was raised from 8 to 24, on the theory that more pipeline depth would
absorb timing jitter (this same lever *did* work once already for
invaders_pico itself — 4→8, see its own DEVNOTES.md). This hung `setup()`
completely (solid black screen, no signal at all). **Root cause: this
vendored `dvi_init()` hardcodes `q_colour_free`/`q_colour_valid` to exactly 8
elements each** (`queue_init_with_spinlock(..., 8, ...)` in
`src/libdvi/dvi.c`) — not a tunable starting point, a hard ceiling. The 9th
`queue_add_blocking_u32()` call in the population loop blocked forever
(nothing consumes from an unstarted queue), hanging `setup()` before
`g_video_ready` was ever set, so Core 1 never even attempted to start the
DVI pump. Reverted to 8 immediately. **`N_SCANBUF` cannot be raised on this
board without patching the vendored library itself.**

**#10 — the actual, correct fix:** Confirmed on real hardware, in isolation
(the standalone `dvi_test_fruitjam` smoke test — no audio, no CPU emulation,
just a scrolling color-bar pattern), that `dvi_vertical_repeat = 1` produces
a **solid red screen outright** on this Adafruit-fork + low-level-API
combination — not marginal, completely broken. This fork evidently doesn't
support that combination cleanly via the raw `dvi_inst` API (its higher-level
`DVIGFX*` wrapper classes presumably set `dvi_vertical_repeat` correctly
paired with whichever resolution/framebuffer scaling mode they represent,
which the low-level path bypasses). Rather than debug further into
`dvi.c`/`dvi_serialiser.h` internals with no clear fork-vs-upstream diff
available, the pragmatic fix: **stop fighting the library's default.** Left
`dvi_vertical_repeat` at 2 (explicit now, not implicit), and changed the
*renderer* to submit 240 unique scanlines per frame instead of 480 — each
one naturally shown on two consecutive physical rows by the hardware, which
is exactly what repeat=2 means. Added `HAL_VIDEO_SCANLINES_PER_FRAME` to the
`ArcadeHAL` video contract for this (may be less than `HAL_VIDEO_HEIGHT`; a
board sets both, a Machine's renderer must submit exactly
`HAL_VIDEO_SCANLINES_PER_FRAME` times per frame, computing physical-row
content as `i * (HAL_VIDEO_HEIGHT / HAL_VIDEO_SCANLINES_PER_FRAME)`). This
preserved every existing TATE_BY/TATE_BX/LAND_BX calibration constant
unchanged — they're still calibrated against the 480-row physical space, just
now sampled at every other row. Bonus: this also halved Core 0's per-frame
rendering workload.

**Confirmed after this fix:** `dvi_test_fruitjam` alone was clean; the full
game was much closer but still showed a small (~5–10% of screen height),
rhythmically oscillating red region, present at boot and during gameplay,
absent during the quiet "credit inserted, waiting for start" screen — see
#11.

### 11. Default `-Os` build didn't leave enough real-time margin

**Symptom:** After #10, a small, persistent, ~4 Hz-oscillating red glitch
region remained near the top of the screen. Telling clue: it tracked overall
*game activity* (present during attract-mode demo and gameplay, specifically
**absent** during the idle "waiting for start" screen) rather than
correlating with sound-effect triggering specifically — pointing at general
CPU/render throughput margin rather than a specific remaining ISR/flash-
residency bug.

**Cause:** This board's Arduino menu defaults to `Tools → Optimize → Small
(-Os)` — optimized for code size, not speed. The two hottest loops in this
entire system — `ArcadeCPU_i8080`'s per-opcode dispatch `switch` (run
~33,536 times per frame) and `invaders_video.cpp`'s per-pixel VRAM
bit-testing in `render_scanline()` — are exactly the kind of code that
benefits substantially from `-O2`/`-O3` (inlining, unrolling) that `-Os`
deliberately avoids. Notably, the reference invaders_pico project doesn't
force an optimization level in its CMakeLists.txt either, but evidently had
enough margin regardless.

**Fix:** Switched to `Tools → Optimize → Optimize More (-O2)`. Confirmed
this fully resolved the remaining glitch. Pinned as the permanent default via
a `sketch.yaml` (`default_fqbn: rp2040:rp2040:adafruit_fruitjam:opt=Optimize2`)
in every sketch folder, so this isn't dependent on remembering an IDE menu
setting — **any new sketch added to this project should get the same
`sketch.yaml` treatment**, or should at minimum be tested at `-Os` before
assuming it has adequate margin.

## Reference: HAL contract quirks specific to this board

- **`N_SCANBUF` is hard-capped at 8** by the vendored PicoDVI fork's
  `dvi_init()` — see problem #9. Do not raise it without first patching
  `ArcadeBoard_FruitJam`'s vendored copy of `libdvi`.
- **`dvi_vertical_repeat` must stay at 2** on this fork via the low-level
  API — see problems #8–10. `HAL_VIDEO_SCANLINES_PER_FRAME` (240, not 480)
  is the number every Machine renderer must actually submit per frame.
- **`hal_audio_enter_critical()`/`hal_audio_exit_critical()`** exist
  specifically so Machine-layer mixer code (`invaders_audio.cpp`) never has
  to `#include "hardware/sync.h"` directly — keeps that file portable to a
  hypothetical non-Pico-SDK board.
- **Button-to-game-action mapping deliberately lives in the sketch**, not in
  `ArcadeMachine_Invaders` or `ArcadeBoard_FruitJam` — see `invaders_
  fruitjam.ino`. The board only knows raw `HAL_BTN_*` indices; only the
  sketch (the one place that knows both which game and which board) knows
  that `HAL_BTN_START1` means "player 1 start" for *this* game.

## Reference: build/tooling gotchas specific to Arduino (not the board)

- `arduino-cli`'s library discovery scans `#include`s, not
  `library.properties`' `depends=` (#4).
- `.pio` files must live in the sketch, or be pre-compiled by hand for a
  library (#1).
- Every header shared across libraries needs a distinctive name — the
  installed Arduino core/library ecosystem is large enough that generic
  names collide (#3).
- C code shared with C++ code needs `extern "C"`, unlike the all-C reference
  build (#2).
- The Arduino IDE's sketchbook location is independent of any
  `arduino-cli.yaml` used for scripted builds (#5).
- This board's default optimization level (`-Os`) is not necessarily fast
  enough for real-time work — always sanity-check timing-sensitive code at
  `-Os` before assuming a fix that works at `-O2` will also work at the
  project's actual shipped setting, or just pin `-O2` explicitly as this
  project now does (#11).

## Confirmed working on real hardware (as of this writing)

`input_test_fruitjam`, `dvi_test_fruitjam`, `audio_test_fruitjam`,
`sd_test_fruitjam`, and the full `invaders_fruitjam` game — all five, in
that order, on an actual Adafruit Fruit Jam with the standard Space Invaders
ROM/sample set from `invaders_assets/`.
